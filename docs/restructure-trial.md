# №33. Время реструктуризации при двух значениях MAXDOP

Команда `restructure-trial` запускает одну поставку последовательно на двух восстановленных копиях. На первой сохраняет исходный MAXDOP базы, на второй временно ставит значение из плана. Отдельно измеряет время команды обновления и длительность самой реструктуризации по журналу адаптера. Обновлённые базы остаются на стенде.

## Что подготовить

1. Возьми две отдельные копии на экземпляре из `local/stand.json`. Последний фактический RESTORE каждой базы должен быть восстановлением одного и того же полного набора с RECOVERY. В плане нужны UUID набора из `msdb.dbo.backupset.backup_set_uuid` и точные имена обеих копий. Имена копий должны отличаться от имени исходной базы в бэкапе.
2. Закрой сеансы обновления и останови фоновые операции в этих копиях. Перед командой лаборатория проверит отсутствие чужих активных запросов и пользовательских транзакций. Потребуются доступ к истории восстановления в msdb, просмотр состояния экземпляра и описаний объектов базы, а для второго варианта — право менять MAXDOP базы.
3. Подготовь файл поставки и исполняемый адаптер площадки. Адаптер должен уметь выбрать нужную регистрацию 1С, проверить экземпляр и GUID базы, провести обновление, дождаться окончания и прочитать журнал. Задай одинаковую команду и аргументы для обеих копий. Для файлов поставки и адаптера укажи их фактические SHA-256. В PowerShell хеш файла показывает `Get-FileHash -Algorithm SHA256`.

Например, локальный план `trial.json` имеет такой вид. Значения GUID и SHA-256 замени данными своей поставки и бэкапа.

```json
{
  "Server": "LAB-SQL",
  "BaselineDB": "trial_a",
  "VariantDB": "trial_b",
  "BackupSetUUID": "00000000-0000-0000-0000-000000000001",
  "PackageID": "erp-update-01",
  "PackagePath": "D:\\trial\\update.cfu",
  "PackageSHA256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "AdapterPath": "D:\\trial\\update-adapter.exe",
  "AdapterSHA256": "abcdef0123456789abcdef0123456789abcdef0123456789abcdef0123456789",
  "AdapterArgs": [],
  "VariantMaxDOP": 2,
  "TimeoutSeconds": 7200
}
```

## Как запустить

```powershell
perf-lab restructure-trial -home D:\lab -plan D:\trial\trial.json
perf-lab restructure-trial -home D:\lab -plan D:\trial\trial.json -apply
```

Первая команда создаёт протокол готовности. Она сверяет UUID бэкапа в истории msdb и семейство базы, текущие GUID обеих копий, исходные MAXDOP, совместимость и SHA-256 определений столбцов и индексов. В отчёте указаны дата RESTORE по времени SQL и значение MAXDOP экземпляра. Если значение базы равно нулю, лаборатория учитывает наследование от экземпляра.

Вторая команда обновляет обе копии. Перед запуском каждого адаптера программа регистрирует попытку для конкретного GUID и записи RESTORE. Если обновление оборвалось, для следующего парного замера подготовь две свежие копии. Программа вернёт исходный MAXDOP второй базы и проверит значение чтением из SQL. Если процесс завершился аварийно и остался журнал, верни настройку той же копии командой

```powershell
perf-lab restructure-trial -home D:\lab -plan D:\trial\trial.json -recover
```

## Что получает и возвращает адаптер

Perf Lab запускает исполняемый файл напрямую. Аргументы берёт из `AdapterArgs`. Параметры конкретной копии передаёт через переменные окружения.

| Переменная | Значение |
| --- | --- |
| `PERFLAB_TRIAL_ID` | Уникальный идентификатор этого запуска адаптера |
| `PERFLAB_SQL_SERVER`, `PERFLAB_SQL_DATABASE` | Проверенный экземпляр SQL и точное имя текущей копии |
| `PERFLAB_DATABASE_GUID`, `PERFLAB_BACKUP_UUID` | GUID копии из `sys.database_recovery_status` и UUID исходного полного набора |
| `PERFLAB_PACKAGE`, `PERFLAB_PACKAGE_ID`, `PERFLAB_PACKAGE_SHA256` | Абсолютный путь к поставке, её ID и SHA-256 |
| `PERFLAB_MAXDOP` | Проверенное значение MAXDOP базы на этот запуск |

Адаптер проверяет цель и поставку перед применением. После окончания он читает из журнала фактические начало, конец и число завершённых операций реструктуризации, сохраняет отдельный непустой файл журнала и рассчитывает его SHA-256. Задай единое правило подсчёта операций для обеих копий. Ошибка обновления или отсутствие нужных записей должны завершить адаптер с ненулевым кодом. Служебный вывод обновления направляй в файл. В stdout верни один UTF-8 JSON объёмом до 64 КиБ. Ниже показан формат ответа.

```json
{
  "Version": 1,
  "Event": "restructure-completed",
  "TrialID": "идентификатор из PERFLAB_TRIAL_ID",
  "Server": "LAB-SQL",
  "Database": "trial_a",
  "DatabaseGUID": "GUID проверенной копии",
  "BackupSetUUID": "UUID полного набора",
  "PackageID": "erp-update-01",
  "PackageSHA256": "SHA-256 применённого файла",
  "Started": "2026-01-12T08:02:10.231Z",
  "Finished": "2026-01-12T08:07:19.752Z",
  "Operations": 3,
  "EvidencePath": "D:\\trial\\logs\\trial_a_run01.log",
  "EvidenceSHA256": "SHA-256 этого файла журнала"
}
```

Время обоих событий должно попасть в интервал работы адаптера. Используй часы узла лаборатории или синхронизированные метки UTC. Отсчёт идёт с точностью до миллисекунды. Perf Lab привязывает ответ к конкретному запуску, проверяет хеш журнала и повторно сверяет поставку. После обновления SQL должен подтвердить изменение схемы в той же копии при заданном MAXDOP.

## Что читать в отчёте

В JSON и HTML сохраняются время начала и окончания команды, её код выхода, длительность, обе метки журнала, число завершённых операций и SHA-256 журнала. Итоговая таблица появляется, если обе схемы после обновления совпали и адаптер подтвердил одинаковое число операций. По хешу можно проверить исходный файл журнала на стенде.

Каждый вариант выполняется один раз, сначала A, затем B. На время могут повлиять порядок прогонов, кэш и соседние нагрузки. Совпадение схем и источника восстановления не подтверждает равенство всех значений строк на момент запуска. Это измерение конкретной поставки на этих копиях. Фактическую степень параллелизма отдельных SQL-операторов проверяют по планам выполнения.
